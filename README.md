# flowdini-cli

Автономный рантайм исполнения ролей flowdini. Сам читает SPEC, сам вызывает
LLM-провайдеров через их API, сам держит MCP-клиент к `vv-db-mcp`, сам пишет
журнал. **Без Hermes / Codex / Claude Code** — внешних агентов нет.

`flowdini-engine` — детерминированная библиотека (планирование, валидация,
снапшоты). `flowdini-cli` — исполнитель поверх неё.

## Установка и запуск

```bash
npm install
npm run build

flowdini run <taskDir> \
  --spec fd.spec.yaml \
  --providers fd.providers.yaml \
  --vvdb ~/work/vv-db-mcp \
  --connection mssql \
  --max-steps 8 \
  --dry-run
```

Флаги:

- `--spec <path>` — SPEC-конфиг; по умолчанию `fd.spec.yaml` в cwd.
- `--providers <path>` — конфиг провайдеров; по умолчанию `fd.providers.yaml` в cwd.
- `--vvdb <dir>` — каталог `vv-db-mcp` (если задан — подключается MCP к БД, резолвится в абсолютный путь).
- `--vvdb-config <path>` — конфиг подключения vv-db-mcp; по умолчанию `<vvdb>/.connect.json`.
- `--connection <name>` — имя коннекта БД для vv-db-mcp; по умолчанию `mssql`.
- `--vault-root <path>` — корень vault для `context`/`fd-vault`; по умолчанию `<taskDir>`.
- `--max-steps <n>` — лимит шагов за запуск (целое ≥ 1); по умолчанию 20. Проверяется до подъёма MCP.
- `--dry-run` — не писать в журнал; печатать раздел в stdout. Пропускается только
  `execute_sql` (БД не меняется), остальные MCP-инструменты вызываются реально.

Ключи провайдеров не лежат в конфигах — только имя переменной окружения
(`apiKeyEnv`); сами ключи экспортируются в окружение.

## Конфиги

`fd.spec.yaml` — SPEC-конфиг (см. канон `flowdini-engine/README.md`):
роли, `reviewLimit`, матрица инструментов (`roles[].tools`), `roles[].model`.

`fd.providers.yaml` — маппинг `модель → провайдер`:

```yaml
providers:
  deepseek:
    baseUrl: https://api.deepseek.com/v1
    apiKeyEnv: DEEPSEEK_API_KEY
    models: [deepseek-v4-pro]
  routerai:
    baseUrl: https://routerai.ru/v1
    apiKeyEnv: ROUTERAI_API_KEY
    models: [claude-sonnet-4, gpt-4o]
```

Модель роли (`roles[].model`) ищется в списках `models` провайдеров; если модель
не закреплена — прогон останавливается с ошибкой.

## Цикл исполнения

`nextStep` → `roleBrief` → агент-роль (LLM + инструменты MCP) → раздел журнала →
`taskCheck` → снапшот (после `CODE`/`FIX`). Останавливается, когда:

- `nextStep` вернул `null` (DONE или нет открытых дуг);
- следующая дуга адресована `HUMAN.*` — рантайм не исполняет людей, ждёт их
  вручную (в т.ч. гибридный гейт `## Q` к `HUMAN.CODER`);
- сбой (ошибка SPEC, роли, сверки плана, снапшота, недоступный инструмент MCP) —
  exit-код 1;
- исчерпан `--max-steps` при открытых дугах — exit-код 0 с подсказкой «запусти снова».

Запуск продолжает журнал: можно гонять многократно, каждый раз исполняется
очередной AI-шаг до первого `HUMAN.*` или DONE. Полного детерминированного
повтора нет — каждый шаг делает новый LLM-вызов; но штатное продолжение
стартует от уже записанного журнала (`taskCheck` проверяет его до агента).

## Аварии, снапшоты, база знаний

- **CRASH**: при детерминированном сбое (`taskCheck` на выходе роли, исключение
  раннера) в журнал пишется `# CRASH n` — терминальный маркер, ход не даётся,
  DONE не ставится. Тело — подсказка + ошибки в тильда-fence, при `taskCheck` —
  сырой ответ модели. Новый `# ISSUE` его не снимает — прогон останавливается
  (`isCrashed`) при любом сохранившемся `# CRASH`; переоткрытие — вручную удалить
  маркер `# CRASH` из журнала и перезапустить.
- **Снапшоты**: после `CODE`/`FIX` рантайм пишет снимок всех объектов в
  `snapshots/<iteration>/`; первый — `snapshots/baseline/` (итерационный снимок
  «до всех изменений», снимается при первом входе кодера после сверки плана).
  Снимок фиксируется (манифест) только при полном наборе; при неполном — ошибка
  в `result.errors` и стоп, базовый манифест не пишется, чтобы следующий запуск
  доснял его по-новому.
- **`knowledge-candidates.md`**: кандидаты в базу знаний (объектные описания +
  резюме) — отдельный файл в `<taskDir>`, не индексируется `taskCheck` (как
  `issue-draft.md`/`issue-dom.md`), то есть не участвует в дугах журнала.

## Инструменты БД (MCP)

`--vvdb <dir>` поднимает `vv-db-mcp` как stdio-подпроцесс. Роли получают
инструменты по `roles[].tools` SPEC (через `resolveRole`). Кодер — `execute_sql` /
`get_definition`, аналитик/ревьюер — read-only (`get_definition` / `describe_*`).

Лог вызовов MCP не ведём (решение владельца, 2026-11-22): аудит — журнал таска
+ снапшоты.

## Модули

- `config.ts` — конфиг провайдеров + `model → провайдер`.
- `llm.ts` — OpenAI-совместимый клиент (`chat/completions`, fetch).
- `agent.ts` — tool-calling цикл роли.
- `mcp.ts` — MCP-клиент к `vv-db-mcp` (stdio).
- `driver.ts` — цикл исполнения.
- `cli.ts` — точка входа.
